# 01 - Business Requirements Document (v1)

Owner: engineering (final revision: Sprint 7). Status: v1, Sprint 0.

## 1. Problem
When a production incident hits a large organisation, the expensive part is rarely the fix.
It is the forty minutes spent working out that something is really wrong, the wrong people
paged, the war room where nobody knows which hypothesis is current, the remediation applied
twice because the first attempt timed out, and the customer email that contradicts what the
engineers already know. Tooling exists for each fragment (monitoring, paging, chat, ITSM),
but the connective tissue - shared state, governed action, institutional memory - is human
willpower at 3 a.m.

## 2. Product
SignalForge is an enterprise incident command centre. It ingests an application's existing
telemetry through public contracts, detects and corroborates trouble, proposes (never
declares) incidents, runs the war room with paging and escalation, maintains an explainable
incident graph with versioned hypotheses, gates every remediation behind policy and human
approval, validates recovery independently, and turns every incident and drill into
searchable institutional memory. Any application onboards through the same contracts; no
app-specific code enters the core (enforced continuously by check_clean.sh).

## 3. Goals and non-goals
Goals
- G1 Cut time-to-detection and time-to-corroborated-proposal (minutes, not tens of minutes).
- G2 Make every AI contribution explainable, versioned and grounded; humans keep authority.
- G3 Make remediation provably safe: policy floor, approvals, uncertain-outcome reconciliation.
- G4 Make onboarding a product flow (wizard + contracts), not an integration project.
- G5 Make audit and learning first-class: hash-chained events, replay, PIR, drills.

Non-goals
- Replacing monitoring/APM vendors (we integrate through adapters).
- Autonomous remediation. High-risk actions can never auto-execute - this is a floor,
  not a preference.
- Multi-machine deployment topology in this build (single machine, no Docker; Postgres-ready).

## 4. Personas
- Org Owner - sets up the org, apps, policies, integrations.
- Incident Commander (IC) - declares, runs the room, approves high-risk actions, closes.
- Tech Lead / SME - investigates, executes approved actions, answers pages.
- Comms Lead - drafts and approves customer/stakeholder communications.
- Executive - consumes status, approves executive comms; explicitly denied operational power.
- Auditor - read-only access to the sealed record, replay and PIR.
- App team - onboards their service through the wizard and observe/ingest contracts.

## 5. Capabilities (traceable)
The requirement catalogue is specs/requirements.yaml (51 REQs); the live mapping to tests
is docs/20-RTM.md, generated by make rtm. Areas: engineering-guide foundations (S0),
platform and identity (S1), event backbone (S2), integrations and onboarding (S3),
detection and lifecycle (S4), war room (S4), incident brain (S5), governance and
execution (S6), drills and audit (S7).

## 6. Success measures
- Detection: sustained anomaly to corroborated proposal within two evaluation windows in
  the reference drill.
- Safety: zero paths to auto-execution of high-risk classes (tested); every gateway
  decision auditable with rules hit.
- Explainability: every copilot claim cites a graph node (ai-eval grounding suite green).
- Resilience: LLM revoked mid-incident degrades visibly and the system continues.
- Onboarding: the reference harness onboards fully through the UI with no seeds.
- Traceability: make evidence REQ-xxx pulls runtime events live in the final demo.

## 7. Constraints and assumptions
- One machine, no Docker; Java 17 (reference harness), Python 3.11, Node 20; SQLite WAL
  (Postgres-ready); local Prometheus/Grafana binaries.
- LLM access only through the configured organizer endpoint; model ids swappable by config;
  deterministic degraded mode is mandatory.
- The reference harness under reference-app/ is demo data, not product: deleting it leaves
  a working product.

## 8. Risks
- R1 LLM latency/availability -> mitigated by cache, budgets, degraded mode (REQ-051).
- R2 Action executed but response lost -> UNCERTAIN state + reconcile-before-retry (REQ-062).
- R3 Prompt injection via telemetry/chat -> threat model AI rows + security tests (REQ-018, S7 probes).
- R4 Scope: 8 sprints, one machine -> playbook discipline, one task at a time, RTM continuously.
